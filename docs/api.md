# Contracts and API

The maintained Python sources are in `contracts/src`. `python3 scripts/contracts.py` produces standalone deployment files. Every deployment pins the runner in its first line. JSON arguments are canonical UTF8 objects with sorted keys and compact separators. Commitments use SHA256 of those canonical bytes. Byte commitments use SHA256 of the original record bytes.

## Request bindings

A correction or dependency contains `request_id`, `owner`, `parties`, `policy_id`, `policy_revision`, `subject_id`, `subject_digest`, `source_manifest_digest`, `consumer`, `consequence_digest`, `generation`, and `deadline`. Addresses contain 20 bytes. IDs contain one to 96 ASCII letters, numbers, dots, underscores or colons. Digests are 64 lowercase hexadecimal characters. Party lists have at most eight addresses. Policy revisions and graph ranks fit unsigned 32 bit counters. Generations fit unsigned 64 bit counters. Deadlines are positive epoch seconds evaluated using GenVM's transaction datetime.

The source manifest digest commits to the complete ordered revision records. A dependency commits to its direct source records. A correction commits to exactly its old and new records. The decision digest commits to the complete original dependency request. None of these fields can change after registration.

A revision contains `request_id`, `revision_id`, `source_id`, `authority_id`, `channel`, `url`, `byte_size`, `byte_digest`, `scope`, `spans`, and `supersedes`. Each span contains `id`, `start`, `end`, and `digest`. Offsets use raw UTF8 bytes, with an exclusive end. A witness ID is `raw_byte_digest:span_id`; the manifest maps it to the exact raw byte interval. UTF8 fragments and forged commitments are rejected. Full records are retained through immutable source URLs and hashes, not private originals in state.

A proposition contains `id`, `statement`, `materiality_question`, `old_span`, `new_span`, and every controlling `rule_id` in `rule_ids`. A dependency reference contains `revision`, `proposition`, `span`, and that complete `definition`. Definitions are locked against the source revision and policy. Statements and materiality questions have at most 1000 characters each.

## Constructors and permissions

| Contract             | Constructor                       | Owner                                                                                   |
| :------------------- | :-------------------------------- | :-------------------------------------------------------------------------------------- |
| RevisionRegistry     | No arguments                      | Deployment sender                                                                       |
| ImpactCourt          | Registry address                  | Deployment sender                                                                       |
| DependencyDispatcher | Court address, registry address   | Authenticated source contracts and consumer owners control their respective transitions |
| ListingConsumer      | Owner address, dispatcher address | Explicit owner                                                                          |
| DeploymentConsumer   | Owner address, dispatcher address | Explicit owner                                                                          |

Registry `bind_court` and Court `bind_dispatcher` belong to the deployment owner. Repeating the identical binding is allowed. A different binding is rejected. New schemas require fresh deployments and explicit application configuration.

| :------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

`receive_binding`, `receive_notice`, and `receive_acknowledgement` accept only the bound dispatcher. `confirm_delivery` accepts only the notice's registered consumer. `replay_notice` and `replay_certificate` are public sponsorship operations; they reemit existing certificates and cannot create verdicts. `validate_acknowledgement` is a conservative public preflight. Positive acknowledgement still requires the authenticated finalized callback.

## Results and lifecycle

Certificates retain every request binding, `status`, the proposition `decisions`, `coverage`, `unresolved`, `superseded_by`, old and new revision IDs, proposition definitions, complete manifests, and `certificate_digest`. Each decision contains `proposition_id`, `impact`, `old_support`, `new_support`, `material`, controlling `rule_ids`, canonical `witness_ids`, and required `action`.

Impact classes are `NONMATERIAL`, `QUALIFICATION`, `CONTRADICTION`, and `RETRACTION`. Support values are `TRUE`, `FALSE`, and `UNRESOLVED`. Required actions are `KEEP`, `REFRESH`, `QUARANTINE`, and `UNRESOLVED`. Prose does not participate in agreement. All policy rules and the fixed controlling span pair participate in the independently grounded vector.

Requests move from `PENDING` to `ASSESSED` or `UNRESOLVED`. `ASSESSED` is terminal within the court; the dispatcher labels its authenticated certificate `FINALIZED`. A pending or unresolved request can become `TIMEOUT` after its transaction deadline. Timeout produces a finalized unresolved notice if no certificate existed. An unresolved or timed out request can be replaced through an otherwise identical `open_correction` containing `supersedes_request`, a unique ID, the next generation and a new deadline. The original becomes `SUPERSEDED`, retaining its certificate and `superseded_by`. The court limits committed assessment attempts for an evidence pair to three. Failed transactions roll back that counter; the service journal separately records and bounds three submitted assessment operations, including finalized failures. Direct callers of the public contract bypass the journal. Malformed model output and VM errors cannot create a certificate.

Delivery moves from `BROADCAST` to `DELIVERED` when the consumer's authenticated finalized confirmation arrives. Acknowledgements retain their operation IDs and generation. A race that supersedes a pending acknowledgement produces a finalized `REJECTED` delivery response, clearing the pending operation without clearing evidence restrictions. Refresh never reverses an irreversible historical payout.

## HTTP routes

Public GET routes: `/api/snapshot`, `/api/generation`, `/api/sources?revision=...`, and `/api/dispatch?request=...`. Snapshot shows the most recent 500 indexed records, 100 timeline events and 50 requests for an authenticated account. This is a bounded workspace projection. The contracts and history cursor APIs preserve the complete record.

POST `/api/commands` requires a verified Privy email bearer token, the configured Origin and a maximum 30000 byte body. Its discriminated command schema is exported from `src/lib/shared/schema.ts`. It accepts revision registration, correction opening, dependency configuration, assessment, paged dispatch, acknowledgement with optional replacement certificate ID, notice replay, deadline expiry, consumer deployment and consumer action. Ownership is checked before signing and again by the contracts. Journal IDs include the target contract address, so a successor deployment cannot reuse a finalized historical operation. Logical contract request IDs are unchanged. Identical requests for the same target are idempotent; conflicting reuse returns HTTP 409. A finalized failed assessment can create a distinct signed retry operation, with at most three journal submissions per request; pending and successful operations are reused. Each identity can enqueue ten operations per minute.

Source comparison also permits the three labeled integration fixtures under the configured app origin. It permits no other app paths or redirects.

POST `/api/commit` prepares a nonauthoritative public source preview. It retrieves complete bounded records from approved hosts, commits exact bytes, and journals the explicit observer configuration. Registration remains a separate signed transaction. GET `/api/worker` requires the private scheduler bearer secret. It never accepts a private semantic verdict.

The service returns request IDs and lifecycle status, never raw signing keys, ciphertexts, signed transaction bodies, authentication tokens or service credentials. Errors expose a recovery message rather than internal exception content.
